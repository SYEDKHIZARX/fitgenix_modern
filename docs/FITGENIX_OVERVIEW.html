01 Executive summary

FITGENIX is an adaptive, injury-aware fitness coach. The original application was a powerful but monolithic Streamlit app. We extracted the brain, exposed it via API, and rebuilt the body as a mobile-first web product.

Problem

One 2,300+ line Streamlit file mixed UI, auth, database, ML, and HTML plan rendering. Great for demos; weak for product UX and multi-client future (web + mobile).

Approach

Keep GA/RL/plan rules in Python (core/). Serve them via FastAPI. Rebuild UX in Next.js with a Neon Coach design system. Streamlit remains as a transitional entrypoint.

Outcome so far

Working web app (onboarding → plan → home → train → RL feedback). Engine tests green (120). API live. Cloud multi-user persistence and full feature parity still planned.

Guiding principle: The differentiator is adaptive intelligence (GA + personalized RL + injury-aware programming). Modernization improves delivery and UX — it does not replace the science with a static workout template.

02 What the old application was

Understanding the Streamlit app is essential so nothing valuable is lost in migration.

Product capabilities

  • 39+ training modalities, goal clusters
  • Split-first programmes (PPL, upper/lower, full body, single-muscle)
  • Equipment tiers & experience scaling
  • Injury maps, severity filters, rehab protocols
  • Genetic Algorithm calorie / intensity scoring + personal retrain
  • Q-learning intensity recommendations + personal Q-table
  • Done / Skip / Too hard outcomes + safety caps
  • Daily readiness check-in → autoregulation
  • Plan lifecycle (adherence, resume ramp, deload, start fresh)
  • Streaks, badges, Plotly charts, PDF export
  • Supabase auth + per-user history, plans, outcomes

Structural pain points

  • Monolith — UI, DB, ML, HTML all in streamlit_app.py
  • Streamlit UX ceiling — full reruns, sidebar-heavy, desktop bias
  • Plan as HTML iframe — fixed heights, hard to interact on mobile
  • Generate-first IA — “report” over “train today”
  • Fragile tests — source-sliced engine loading
  • No client API — could not power a real web/mobile shell cleanly

05 How the new application works

End-to-end flow for a user on the modern web app.

→
2 Generate plan (API → core)
→
3 Home · readiness
→
4 Train · outcomes
→
5 RL feedback

1 · Onboarding

User picks goal cluster & style, experience, equipment, split & days, body metrics, optional injury. Profile is stored (browser for now). First plan is requested from the API.

2 · Plan generation

POST /api/generate-plan maps profile → get_plan_data in core: split schedule, equipment filter, injury blocks/modifies, rep schemes, 7-day structured JSON (not HTML).

3 · Daily Home

Optional check-in pills (sleep, soreness, energy) → /api/readiness using real readiness weights/bands. Session card shows Day N focus + preview + Start CTA. Coaching banner summarizes next action.

4 · Train mode

Full exercise list with large Done / Skip / Too hard controls. Optional swap loads injury- & equipment-aware substitutes. Autoreg may reduce sets if readiness is low (when check-in exists).

5 · Learning signal

End session sends outcomes to /api/rl/feedback (Q-update math). Intensity tip comes from /api/rl/recommend. Personal long-term Q-table storage is the next backend step.

6 · Plan · Progress · Profile

Week timeline, regenerate plan, history list, edit body/training/injury and re-plan. Charts/PDF/rehab depth still expanding toward Streamlit parity.

07 Future plan

Phased roadmap so product depth catches the old app — then exceeds it.

Phase A · Now / next sprint

Cloud identity & memory

Supabase auth on the web app. API validates JWT. Persist profile, active plan, check-ins, exercise outcomes, personal Q-table, GA weights, injury profile. Same user, any device — true replacement for Streamlit’s memory.

Phase B

Coach loop parity

Full plan lifecycle from real adherence gaps (resume ramp / deload / start fresh). Progression from past outcomes. Activity logging (steps / active minutes). Personal RL tip from stored Q-table. Adaptation badges when something real changed.

Phase C

Report & depth features

Rehab protocol screens, progress charts, streaks/badges, PDF export endpoint, model performance transparency, optional exercise demos / form cues.

Phase D

Product API v1 & mobile

Versioned public API (/api/v1), OpenAPI client generation, observability. Then Expo / React Native app consuming the same API. PWA install as interim “app.”

Do not start native mobile until auth + persistence and the daily loop are stable in production on web. The engine is ready; the product memory is the blocker.

08 How to run today

API

From project root:

pip install -r requirements.txt uvicorn api.main:app --reload --port 8000

Health: http://127.0.0.1:8000/api/health

Web

cd web npm install npm run dev

App: http://localhost:3000

If port 3000 is busy (old Vite), free it or use npx next dev -p 3001.

Engine tests

pytest -v tests/test_engine.py

Legacy Streamlit

streamlit run streamlit_app.py

Still uses core for pure logic; Supabase auth/DB intact.
